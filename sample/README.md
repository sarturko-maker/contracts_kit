# Invented sample and expected outputs

Everything here is synthetic development data. Names, dates, signatures, account numbers,
documents and trading practices are invented. The fixed review date is **6 September 2026**.
The drawn signatures identify no real people. Dates on doc 001's signature page exist only
in the page image; the NDA has no native text at all.

Run stage 1 on `sample/pile` using the repository README. Treat `expected/` as an answer key
for review after the run; it is not a substitute for reading the sample files.

The ERP has two accounts and one stream row. Tallowfield Industries' signing entity is
Tallowfield Industries (North) Limited, its parent is Oxbrook Holdings plc, and its named
German affiliate is Tallowfield Industrie GmbH. The other account is Pellmont Logistics Group.
Our invented entity is Marrowgate Supply Ltd.

`expected/cards` contains nine JSON and Markdown cards. `expected/placements`, `entity-map.csv`
and `our-entities.csv` are explicit fixture decisions. `expected/forms` contains nine validated
forms with commercial topics off. `expected/trees` records family proposals; the C1 proposal is
uncertain because the form cannot explicitly encode the deemed participation structure.
`expected/notes` and the replay logs are generated by the kit's scripts.

The audit corpus has ten rows: nine readable documents plus the unreadable-file row. The account
register has three ERP rows, of which two are main accounts and one is a stream. Review columns
are deliberately blank for legal and sales. See BUILD-NOTES.md for these resolutions of the brief's
conflicting row-count requirements.

To regenerate development fixtures, with build-only ReportLab and Pillow installed:

```sh
python sample/make_pile.py
python sample/make_expected.py
python -m unittest discover -s tests -p test_sample.py -v
```

The expected-output generator runs prepare, sort, place, form validation and graph export inside
a temporary copy of the kit. It does not write the working kit's `work/` or `out/` folders. The
tests use the shipped fixtures and enterprise dependencies only. They check deterministic replay,
not independent model interpretation; the separate README-only handover checks the latter.

For the precedence sabotage case, generate a separate pile, then have a fresh reader and judge
read it. The overlap should become **unresolved**, while the programme remains expired:

```sh
python sample/make_pile.py --output /tmp/dcg-sabotage-pile --omit-precedence
```

Never use either generator on real material. Originals in an enterprise pile are never altered.
